# 用户视角架构

BFB把B站、下载器、本地恢复区和 AList / OpenList WebDAV 连接成一条可观察、可中断恢复的链路。

<div class="workflow-line">
  <span>B站账号与收藏夹</span><i>→</i><span>BFB调度器</span><i>→</i><span>BBDown / aria2 / FFmpeg</span><i>→</i><span>本地会话</span><i>→</i><span>AList / OpenList WebDAV</span><i>→</i><span>网盘</span>
</div>

## 持久化边界

- **SQLite**：视频、收藏夹关系、任务、远端文件、失败、冷却、画质重调、已移除账号快照和归档删除进度。
- **配置与账号JSON**：用户设置、B站登录态和网页日志继续独立保存。
- **下载会话文件**：每个`temp/<BVID>/.bfb-download.json`记录分P CID、已验证输出和恢复信息，不保存Cookie、token或签名下载地址。
- **aria2控制文件**：负责字节级续传；损坏或资源长度变化时只重置对应轨道。

## 为什么既有SQLite又有会话文件

SQLite回答“下一项工作是什么”，会话文件回答“这个BV在磁盘上已经完成了什么”。把两者分开后，调度任务可以用事务和租约恢复，媒体文件也能在BBDown进程中断后按CID重新核对。

归档库同样直接查询SQLite，但不把全库装进运行时缓存：先按查询上下文和BVID选出最多50个分页键，再批量加载本页关系、视频与远端证明。浏览、搜索和翻页不会触发B站请求或 AList / OpenList 目录扫描。

归档删除复用持久任务、租约和心跳，但逐文件清单单独存入SQLite，不塞进任务JSON或进程内存。预览按规范远端路径折叠全局证明和收藏来源证明；执行前先完成全部HEAD预检，再逐文件DELETE并确认不可见。共享路径只清除目标来源证明，只有最后一个来源删除后才清理全局兼容证明。

## 上传为什么分两步

AList / OpenList 接受 PUT 不代表网盘立即能列出文件。普通归档现在直接条件PUT到正式路径，不创建`.bfb-staging`目录，也不依赖WebDAV MOVE；`transfer_sessions`和`remote_files`逐目标、逐文件保存预期路径、大小与确认状态。持久上传会话以代际区分每次尝试，重开时保留旧逐文件明细，旧任务不能覆盖当前代际。只有远端同名同大小文件可见且具有本次Session的PUT证明，才允许确认本次上传并清理本地成品。部分驱动可能在实际写入后返回405，BFB会再次读取精确路径，只有大小一致且该PUT请求确实已发送才确认上传。PUT已接受但暂时不可见时只继续确认，不自动重复传输；超过确认窗口后进入队列里的“重新确认 / 继续上传”，“重新确认”只读检查，“继续上传”才允许本次明确重传。

普通同步以旧归档优先：当前关系有完整路径、大小和确认状态证明且远端一致时，直接保留旧版并跳过新版上传。未知同大小、大小不一致、部分证明或证明漂移都属于受保护的整组冲突；BFB把完整本地分P组PUT到`_conflicts/upload-<任务ID>`，正式旧路径不移动、不覆盖、不删除。候选选择会重新核验两侧证明并串行执行，采用候选后旧证明仍保存在关系审计记录中。画质替换和远程重命名继续使用独立能力探测：MOVE优先，只有明确不支持MOVE且COPY完成目标校验后才删除源文件。

## 关闭与崩溃

正常关闭最多等待20秒保存控制文件、释放租约并checkpoint WAL。归档删除会停止领取新项并等待当前WebDAV请求退出；若超过关闭期限，SQLite保持打开直到请求真正结束。异常退出时，SQLite租约过期后重新领取任务，归档删除从最后已确认文件继续，aria2和会话清单继续恢复磁盘进度。
