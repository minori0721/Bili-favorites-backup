# 更新镜像

稳定版使用`latest`，测试版使用`dev`，版本标签使用`v*.*.*`。生产部署建议固定版本标签；想跟随稳定分支时再使用`latest`。

```bash
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=100 app
```

`docker compose up -d`会用已拉取镜像重建需要更新的容器，不会删除持久化目录。
单容器重建时，旧容器停止到新服务开始监听之间会有短暂不可访问窗口；`docker compose ps`显示运行不等于网页已经就绪。等待访问地址的`/login`正常返回后，再刷新首页检查版本。

## 维护者：只更新镜像内的运行环境

Node.js 安全更新不要求提升 BFB 版本或创建 Release。Dockerfile 的 `node:24-bookworm-slim` 跟随 Node 24 系列，但已有 BFB 镜像不会自动替换其中的 Node。

1. 在仓库 **Actions → Docker Publish → Run workflow** 中选择 `dev` 或 `main` 分支。
2. 勾选 **仅重建镜像** 后运行。`dev` 更新 DockerHub 的 `:dev`，`main` 更新 `:latest`；不要选择版本标签。
3. 等待整条工作流成功，再在宝塔更新对应容器，或执行本页开头的 `docker compose pull` 与 `docker compose up -d`。

若页面没有该勾选项，先确认默认分支和目标分支均已包含这次工作流更新。

此模式主动拉取最新基础镜像，并重新执行 `runtime-tools` 阶段的系统包安装，避免软件源已有安全更新却仍复用旧安装缓存；其他独立构建阶段继续使用缓存。保留全量测试、构建、隔离启动、媒体工具和登录保护检查；成品必须使用 Node 24.22.1 或更高的 Node 24 正式版本，OpenSSL 系统包通过 `scripts/check-image-runtime.sh` 中的修复版本检查。仅这次明确勾选的手动构建允许同提交文件层发生变化，普通发布仍保留一致性检查。执行期间分支已出现新提交时，不推广过期镜像。

最终运行镜像保留 Node 和应用生产依赖，移除制作镜像时使用的 npm/npx。应用仍由 `node dist/index.js` 启动；需要更改依赖时重新构建镜像，不在运行容器中执行 `npm install`。源码部署和本地开发继续使用原有 npm 命令。

应用版本、Git 标签、正式 Release、dev 预发布页面以及原来的 `:sha-*`、`:revision-*`、`:vX.Y.Z` 镜像标签均不修改。每次重建另存 `:rebuild-<完整提交>-<工作流ID>-<尝试次数>`，在 Actions 中记录镜像摘要与层变化，供检查或回退。固定版本镜像不随该操作更新。

仅重建不会提升包版本；若源码提交也没有变化，网页不会仅因本次重建显示“新版本”。检查容器内 `node --version` 和镜像摘要确认修复，原 Release 的固定镜像摘要仍代表原构建。Node 升级会改变基础层，本次拉取量可能增加，不代表层复用失效。

## 更新前检查

::: warning 已有反向代理部署：先检查登录配置
新版本默认不信任代理头。宝塔 / Nginx 反代用户更新前必须设置 `TRUST_PROXY` 为实际代理 IP/CIDR，HTTPS 访问还应设置 `COOKIE_SECURE=true`，并核对代理转发的域名、端口与协议。直连 HTTP 保持两项为 `false`。

自定义 Compose 必须显式传入这两个环境变量，仅修改 `.env` 不够。配置变化需重建应用容器才生效。详见[反向代理与登录安全](./security#反向代理与登录安全)。
:::

- `data/`、`temp/`和内置AList的`alist/`确实挂载到宿主机。
- 阅读[版本与升级记录](../reference/releases)中的迁移说明。
- `v2.7.2` 沿用 `v2.7.0`、`v2.7.1` 的 SQLite schema 12、配置及持久化挂载，无需清空数据或重新下载已有有效归档。桌面入口在侧栏，手机入口在底部导航；归档排除与清理仍须由用户明确选择。回滚镜像不会撤销已执行的远端操作，升级前保留匹配的数据快照与原镜像摘要。
- 涉及 AList / OpenList 版本变化时，先备份对应数据目录并阅读[AList / OpenList升级](../alist/upgrade)。
- 大版本回滚前先导出旧镜像可读取的JSON快照。
- `v2.7.0` 首次启动会将 SQLite schema 11 自动升级到 12，保存 UP 订阅与来源数据。升级前先在数据库旁的 `backups` 目录生成并验证快照与 SHA256 文件，默认文件名为 `data/backups/bfb-before-schema-12-v11-*.sqlite`；备份或迁移失败时停止启动，不会跳过失败继续调度。已运行 schema 12 开发版的用户无需重复该次迁移。
- 回退 `v2.6.5` 或更早版本，必须先停止应用、保留当前数据，再恢复升级前的匹配数据备份。旧版不能直接打开 schema 12；JSON 状态 schema 13 与迁移包清单 schema 3 不变，也不代表旧版可以导入新数据库。回滚不会撤销已完成的远端文件操作，详见[迁移与回滚](./migration#回滚旧镜像)。
- `v2.5.1`会把schema 10数据库升级到schema 11，增加手动来源类型与相关索引；`v2.5.2`至`v2.6.5`沿用schema 11，不再执行数据库结构迁移，不批量探测在线内容、不重写既有关系。升级前会在`data/backups`生成一致性备份，启动期间服务暂不可用；回滚到`v2.5.0`或更早镜像时，先恢复升级前SQLite备份，不能让旧镜像直接打开schema 11数据库。
- 真实升级时，容器日志会显示源schema、目标schema、开始、完成或失败以及总耗时；普通启动不会重复输出迁移日志。失败日志只说明没有提交数据库变更，不包含数据库路径、备份文件名、SQL正文或业务数据。
- 更新前确认没有等待执行、执行中、自动重试或失败待处理的归档删除任务；这些任务会阻止迁移导出和业务状态清理，且开始后不能取消。

- v2.5.6新增导入中断恢复。回退旧镜像前须完成或核实恢复记录，不能手工删记录绕过恢复；详见[迁移与回滚](./migration)。

## 更新后检查

1. 顶部版本与预期镜像一致。
2. 容器没有反复重启。
3. SQLite完整启动，持久任务和冷却恢复。
4. 若涉及schema升级，确认迁移日志完成，在线内容按钮可打开，归档库全局、账号和收藏夹目录均可正常翻页，队列可恢复持久上传与远端确认。
5. 队列没有同一BV的立即失败循环。
6. AList / OpenList 上传与远端确认正常。

拉取失败不会替换当前运行容器；看到旧容器仍在运行并不代表更新成功。
